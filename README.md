# 📚 多文档智能问答系统（RAG 实现）

> 一个**不依赖 RAG 框架、检索内核全部手写**的本地知识库问答系统：自动扫描 `knowledge_base/` 下的文档，用中文向量模型检索最相关的片段，调用大模型生成**带引用来源**的回答；相似度不足时**直接拒答**，不浪费一次 API 调用。

核心是自己写的那部分：切块 → 编码 → 余弦相似度召回 → 拼装带来源编号的 Prompt，没有 LangChain / FAISS / Chroma。

---

## ✨ 亮点

| 亮点 | 说明 |
|---|---|
| 🇨🇳 **中文向量模型** | `BAAI/bge-small-zh-v1.5`（512 维），替换英文模型后检索 hit@5 从 33% → 100% |
| 📊 **评测驱动调参** | 自带 `eval_retrieval.py`（15 条评测问题 + 4 条负样本），切块参数和拒答阈值都是比出来的，不是拍脑袋定的 |
| 🔗 **引用溯源** | 每个片段带 `文件名 #序号`，Prompt 要求模型标注 `[1][2]`，界面同步展示来源与相似度 |
| 🚫 **低分拒答** | 最高相似度低于阈值时直接返回「资料中未找到」，不调用大模型（省钱 + 压幻觉） |
| ⚡ **双层缓存** | `@st.cache_resource` 缓存模型与向量矩阵，二次提问免去 90MB 模型重载 |
| 🧩 **逻辑与 UI 分离** | 检索/生成全在 `rag_core.py`，网页版与命令行版共用同一套逻辑 |

## ⚙️ 技术栈

| 环节 | 选型 | 说明 |
|---|---|---|
| 文本向量化 | `sentence-transformers` + `BAAI/bge-small-zh-v1.5` | 512 维，本地 CPU 运行，首次约 95MB |
| 相似度检索 | `numpy` 手写余弦相似度 | 向量先 L2 归一化，点积即余弦，`argsort` 取 top-k |
| 大模型 | DeepSeek API（`deepseek-v4-flash`） | OpenAI 兼容的 ChatCompletions 接口 |
| Web 框架 | Streamlit | `cache_resource` 缓存模型、`st.form` 合并交互、`ProgressColumn` 展示相似度 |
| 评测 | `eval_retrieval.py` | 关键词匹配做弱标签，不依赖模型打分，结果稳定可复现 |

## 🧠 它是怎么工作的

```
① 切块   按段落/编号/表格行拿到结构块 → 不足 90 字才与相邻块合并 → 硬上限 200 字，重叠 40 字
         每个片段记下出处（文件名 + 序号），这是引用溯源的基础
② 编码   bge-small-zh-v1.5 把每个片段编码成 512 维向量并 L2 归一化 → 矩阵 (N, 512)
③ 提问   问题同样编码成 512 维向量
④ 检索   矩阵 @ 问题向量 = 每个片段的余弦相似度 → 取 top-k（默认 5）
⑤ 判定   最高分 < 阈值（默认 0.40）→ 直接拒答，不进第 ⑥ 步
⑥ 生成   Prompt = 人设 + 带编号的参考资料 + 问题 → DeepSeek → 答案（含 [1][2] 引用）
```

对应代码：`rag_core.py` 的 `split_text` / `load_chunks` / `build_index` / `search` / `build_prompt` / `generate`。

## 📊 参数是怎么定的（不是拍脑袋）

### 1）先把评测集建起来

`eval_retrieval.py` 里有 15 条"问题 → 标准答案关键词"（关键词直接取自原文，如 `45天`、`540次`、`4.5小时`），
外加 4 条知识库里根本没有的问题用来测拒答。跑一次不到 30 秒，所以每次改参数都能立刻看到涨跌。

### 2）切块参数：比了 4 组

| 方案 | 段数 | 平均字数 | hit@1 | hit@3 | hit@5 |
|---|---|---|---|---|---|
| A 尺寸优先 300/50 | 36 | 244 | 67% | 93% | 100% |
| B 结构优先 300/50 | 60 | 165 | 60% | 93% | 93% |
| **C 结构优先 200/40（采用）** | **78** | **130** | **80%** | **93%** | **100%** |
| D 结构优先 400/60 | 54 | 186 | 73% | 87% | 87% |

结论：片段越小、越贴着文档原有结构（一条 FAQ 就是一段），top-1 越准；但太小会让上下文不完整，
所以最终定在 **200 字上限 + 40 字重叠 + 不足 90 字才合并**。

### 3）模型 vs 切块：2×2 消融，看谁贡献大

| 组合 | hit@1 | hit@5 | 相关/无关分数间隔 |
|---|---|---|---|
| 旧切块 + all-MiniLM-L6-v2（原始方案） | 20% | 33% | **-0.273** ❌ |
| 新切块 + all-MiniLM-L6-v2 | 13% | 60% | **-0.255** ❌ |
| 旧切块 + bge-small-zh-v1.5 | 47% | 93% | +0.056 ✅ |
| **新切块 + bge-small-zh-v1.5（现行）** | **80%** | **100%** | +0.015 ✅ |

两个结论：

1. **模型是主要矛盾**（hit@5 +60 个百分点）。英文模型下无论怎么切块，"相关性分数间隔"都是负的
   —— 无关问题的分数比相关问题还高，阈值根本无法设。
2. **切块是次要但必要的**（+27 个百分点），且它把 top-1 命中率从 47% 抬到 80%，直接决定来源面板准不准。

### 4）拒答阈值

- 相关问题 top-1 分数：最低 0.438，平均 0.674
- 无关问题 top-1 分数：最高 0.422，平均 0.374

两类之间只隔着 0.016，取中点 0.43 属于"极限设置"，容易误伤；最终取 **0.40**（偏保守，宁可多问一次模型也别误拒）。
实测：4 条无关问题拦下 3 条，15 条相关问题 0 误拦。

**示例一：能答的问题（真实运行输出，top_k=5）**

```text
问题：电池能用多久？
检索：[1] 0.708 产品手册.txt #10  «完全充电时间：约 4.5小时…»
      [2] 0.684 产品手册.txt #9   «使用敏感呵护模式 → 续航可延长至 50天左右…»
      [3] 0.671 产品手册.txt #11  «…三年内电池衰减可忽略不计…»
      [4] 0.653 常见问题.txt #5   «…剩余电量＜15%，还能用约 5~6 次…»
      [5] 0.613 产品手册.txt #8   «标称续航：45天（每天使用2次，每次2分钟…）»

回答：这题得拆成两问看：一次充电能撑多久，以及电池本身能"服役"多久。
- 日常标准模式：标称续航 **45天**（按每天使用2次、每次2分钟算）[5]。
- 开深层抛光模式：续航约 **38~40天**[5]；敏感呵护模式可延长到 **50天左右**[2][5]。
- 充电时间：完全充电约 **4.5小时**，支持过充保护，整夜插电无风险[1][2][4]。
- 电池整体寿命：按 3 年计算总充电次数约 **80~90次**，远低于设计上限 500 次[1][3]。
- 低电量提醒：红灯闪烁表示剩余电量 **＜15%**，还能用约 **5~6次**[2][4]。
```

注意这个例子里 top-1 是「充电时间」片段，真正回答"能用多久"的 45 天那条排在第 5 ——
**top-1 命中率 80% 就是这么来的**，这类"同一主题散落在多段"的问题正是需要 rerank 的场景（见「已知限制」）。

**示例二：资料里没有的问题（直接拒答，不烧钱）**

```text
问题：今天天气怎么样
检索：最高相似度 0.357 < 阈值 0.40
输出：哎呀，我翻遍了手册也没找到这个问题的答案，要不您换个问法试试？
      （未调用大模型，省下一次 API 调用）
```

## ⚠️ 已知限制

1. **没有 rerank**：top-k 直接按向量相似度排序后进 Prompt。加一层 cross-encoder 重排（如 `bge-reranker-base`）通常还能再涨几个点，代价是延迟翻倍。
2. **纯向量检索，没有关键词兜底**：`IPX7`、`SmartPulse` 这类专有名词，BM25 混合检索会比纯语义更稳。
3. **评测集偏小**：15 条问题 + 4 条负样本，够用来比较参数，但不足以支撑"准确率"级别的结论。
4. **单轮问答**：没有多轮对话历史，追问"那它呢"会失效。
5. **只支持 .txt**：PDF / Word / 网页需要额外的解析层。
6. **索引不落盘**：每次启动都要重新编码（78 个片段约 1 秒，暂时无感；文档变多后需要 Chroma 或缓存到磁盘）。

## 🧠 学习心得

这个项目最大的收获不是"跑通了 RAG"，而是**学会了用评测代替感觉**。

一开始我以为检索效果不好是因为切块没切好，于是反复调切块参数——直到我写了 15 条问题的评测集才发现：
真正的问题是英文 embedding 对中文没有区分度（无关问题的相似度 0.75，比相关问题的 0.58 还高），
切块再怎么调都救不回来。**没有评测的时候，我连自己改的是好是坏都不知道。**

现在这个仓库里保留了两样东西：`eval_retrieval.py` 这个"尺子"，和 README 里那张参数对比表。
下次换模型、换切块策略，跑一遍就知道是涨还是跌。
